# Scalable Model Serving API + Real-Time Dashboard

A model-serving gateway with continuous batching, KV/prefix-cache reuse, Prometheus-instrumented inference nodes, a
live React + Tailwind operations dashboard, runtime configuration, shadow-traffic rollouts, per-tenant auth and
SLO/error-budget alerting, plus deployment configs for GKE (vLLM on L4 GPUs) and Vertex AI.

```
                         ┌────────────── dashboard (React + Tailwind, nginx) ──────────────┐
  clients ──► gateway ───┤ /api/stats · /api/config · /api/shadow · /api/cluster           │
  (API keys, rate limit, │                                                                  │
   load shedding,        └──────────────────────────────────────────────────────────────────┘
   shadow mirroring)
        │  BACKEND=sim            built-in scheduler on a simulated GPU (local dev, CI, tests)
        │  BACKEND=openai_proxy   vLLM / SGLang pods on GPU nodes (GKE) or a Vertex AI endpoint
        ▼
   /metrics ──► Prometheus ──► Grafana + burn-rate alerts          traces ──► OTLP (optional)
```

## What each part does

| Area | Implementation |
|---|---|
| **Batching** | `server/app/engine.py`: vLLM-style continuous batching. The running batch is re-formed every decode step, with a prefill-token budget, a batching window, and a bounded queue that sheds load (503). |
| **KV-cache reuse** | `server/app/kvcache.py`: paged block accounting with chained prefix hashes, refcount pinning and LRU eviction (the idea behind vLLM prefix caching / SGLang RadixAttention). |
| **Real engines** | `BACKEND=openai_proxy` forwards to any OpenAI-compatible server: vLLM (manifest included) or SGLang. Batching and KV reuse then happen inside that engine. |
| **API** | `POST /v1/generate` (JSON or SSE streaming), Vertex AI custom-container contract (`/predict`, `/health`, honours `AIP_*` routes). |
| **Telemetry** | Prometheus: latency / TTFT / queue-wait histograms, queue depth, running batch, batch-size histogram, KV usage, prefix hit ratio, GPU utilisation (NVML when a GPU is present, otherwise simulated), per-tenant counters. Optional OpenTelemetry tracing and `X-Request-ID` propagation. |
| **Dashboard** | Live GPU util, p50/p95/p99, queue and batch charts, KV and prefix-cache gauges, SLO burn rate, per-node table (via Prometheus), runtime-config editor, shadow-rollout controls. |
| **Runtime config** | `PUT /api/config` changes batching, window, budgets, queue limit and timeout live, with no restart. |
| **Shadow rollouts** | `PUT /api/shadow` mirrors a share of live traffic to a candidate configuration. Clients only see the primary's response; p50/p95 and output match are compared on the same requests, then `POST /api/shadow/promote` applies the candidate. |
| **Multi-tenant access** | API keys (SHA-256 hashed in memory) mapped to tenants, per-tenant token-bucket rate limits, admin-only writes, NetworkPolicies that keep vLLM reachable only from the gateway. |
| **SLOs** | `deploy/prometheus/rules.yml`: multi-window burn-rate alerts (14.4× page, 6× ticket) for a 99.5% availability SLO, latency SLI, queue, GPU and shadow-regression alerts. Grafana dashboard is generated by `deploy/grafana/gen_dashboard.py`. |

## Quick start (no GPU, no cloud account)

```bash
make install            # python venv + dependencies
make test               # 17 engine/cache tests + API tests
make run                # API on http://localhost:8000

make dashboard-install  # in a second terminal
make dashboard-dev      # dashboard on http://localhost:5173

make load               # in a third terminal: drives traffic so the charts move
```

Everything in one go: `make up` (API, dashboard :8080, Prometheus :9090, Grafana :3001, login `admin`/`admin`).

```bash
curl -s localhost:8000/v1/generate -H 'content-type: application/json' \
     -d '{"prompt": "Explain continuous batching", "max_tokens": 32}'
```

## API

| Endpoint | Purpose |
|---|---|
| `POST /v1/generate` | `{prompt, max_tokens, stream}` → text, usage (incl. cached tokens), timings. `stream: true` returns SSE. |
| `POST /predict` | Vertex AI contract: `{"instances": [...], "parameters": {...}}` → `{"predictions": [...]}` |
| `GET /healthz`, `/readyz`, `/health` | liveness / readiness |
| `GET /metrics` | Prometheus exposition (restrict with NetworkPolicy; it is unauthenticated) |
| `GET /api/stats`, `/api/history`, `/api/cluster`, `/api/info` | dashboard data |
| `GET/PUT /api/config` | read / change runtime settings (admin for PUT) |
| `GET/PUT/DELETE /api/shadow`, `POST /api/shadow/promote` | shadow rollout control (admin for writes) |

Errors: `401` bad key · `403` not admin · `413` request can never fit the KV cache · `429` tenant rate limit (`Retry-After`) ·
`503` load shed (`Retry-After`) · `504` request timeout · `502` upstream failure.

Auth is off by default for local use. Enable it with `AUTH_ENABLED=true` and `API_KEYS_JSON`
(`{"sk-...": {"tenant": "team-a", "rps": 50, "burst": 100}, "sk-ops": {"tenant": "ops", "admin": true}}`).

## Configuration

Startup settings are environment variables (`server/app/config.py`): `BACKEND`, `UPSTREAM_URL`, `UPSTREAM_MODEL`,
`KV_CACHE_BLOCKS`, `AUTH_ENABLED`, `API_KEYS_JSON`, `SLO_AVAILABILITY`, `SLO_LATENCY_MS`, `PROMETHEUS_URL`, `CORS_ORIGINS`,
`SIM_*` (cost model). Runtime settings (changeable live): `enable_batching`, `enable_prefix_cache`, `max_batch_size`,
`max_batch_tokens`, `max_wait_ms`, `max_queue`, `request_timeout_s`.

## Benchmarks (simulated GPU, measured here)

`make bench` runs the scheduler in-process against a cost model (decode step = 6 ms + 0.12 ms per sequence, prefill = 0.04 ms
per uncached token). Workload: 4 shared 400-token system prompts + a unique 30-token suffix, 16–64 output tokens.
Results from one run (`bench/results.json`), 32 concurrent clients:

| mode | req/s | tokens/s | p50 | p95 | p99 | prefix hit |
|---|---:|---:|---:|---:|---:|---:|
| naive (one sequence at a time) | 3.4 | 129 | 8513 ms | 10242 ms | 10296 ms | 0% |
| continuous batching | 32.1 | 1240 | 962 ms | 1573 ms | 1756 ms | 0% |
| batching + prefix cache | 61.5 | 2379 | 497 ms | 786 ms | 1161 ms | 87% |

Prefix caching adds about 1.9× throughput and halves p95 on top of batching; batching alone is about 9× over the naive baseline.
Open-loop (Poisson) sweep of one node in optimized mode: p95 stays under 1.2 s up to ~100 req/s and climbs past it
(3.3 s at 125 req/s, 4.9 s at 150), so a single simulated node saturates near 100–125 req/s.

**These numbers describe the simulator, not real hardware.** The cost model is an assumption, and the naive baseline is a
deliberately simple request-at-a-time server. Do not quote them as GPU results.

### Measuring on real GPUs

Run the same comparison against vLLM on your own cluster, using this repo's load generator and dashboard:

1. Baseline: vLLM with `--max-num-seqs=1 --no-enable-prefix-caching` (or your existing TorchServe/TensorRT deployment).
2. Candidate: vLLM defaults plus `--enable-prefix-caching`.
3. Drive both with `loadtest/loadtest.py --rps N --duration 120` at the same offered load and compare p50/p95 and achieved req/s
   (Grafana's latency and throughput panels show the same data).
4. For aggregate throughput targets such as 1k+ RPS, scale replicas: a single node saturates at its own limit, and the gateway HPA
   plus the L4 node pool (autoscaled) provide the horizontal scaling.

## Deploying

**GKE** (`deploy/gke/create_cluster.sh`, `deploy/k8s/`): CPU pool for the gateway and dashboard, an autoscaled L4 GPU pool for
vLLM (node selector + affinity + toleration), gateway HPA on CPU, PodDisruptionBudget, NetworkPolicies, Google Managed Prometheus
`PodMonitoring` and a `Rules` resource generated from `deploy/prometheus/rules.yml` (`make rules`). vLLM-queue-based GPU autoscaling
is provided as an optional manifest (`vllm-hpa.yaml`) because it needs a custom-metrics adapter.

**Vertex AI** (`deploy/vertex/deploy.py`): uploads the container, creates or reuses an endpoint and deploys with GPU autoscaling.
Vertex canary rollouts are traffic splits (`--traffic-percentage`), distinct from the gateway's request mirroring.
